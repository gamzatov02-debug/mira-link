# MIRA LINK DESIGN SYSTEM — FOUNDATION DECISIONS

This log records decisions needed to turn the Stage 1 audit and Stage 2 architecture into one future design-system foundation. It does not change the current interface, implementation or domain contract.

| ID | Question | Current conflict | Decision | Reason |
|---|---|---|---|---|
| FD-001 | Which typeface leads MIRA LINK? | The product shell uses local Manrope while Guest styles scope Inter. | **Manrope is the sole primary family** for Website, Guest, Waiter and Admin. Inter remains untouched as a legacy implementation source until an approved migration. | Manrope is already locally licensed and used in the principal product shell. One family gives the product a coherent, calm and precise voice. |
| FD-002 | How should the brand colour be expressed? | Supporting green and gold UI shades had been presented as the MIRA base colours. | Official identity values are `color.brand.green` `#0A1D08` and `color.brand.gold` `#C89B3C`. Supporting UI greens and golds remain separate primitives for surfaces, states and accessibility. | Brand identity must not be silently replaced by implementation-supporting shades; a change requires a separate Customer decision. |
| FD-003 | Is a global dark-mode toggle required? | The current product is predominantly dark, while operations need lighter high-density contexts. | **NOT REQUIRED FOR MVP DESIGN SYSTEM.** Product surfaces choose a documented dark brand/restaurant or light operational context; this is not a user preference at this stage. | It avoids treating one visual environment as a universal setting while preserving clear expansion room. |
| FD-004 | How are colours governed? | CSS contains duplicated values and role meanings across global, MIRA and Guest style layers. | Define primitive values privately and expose semantic aliases for future components. | Semantic roles make accessible updates and venue validation possible without broad literal-value replacement. |
| FD-005 | How far can venue branding change the product? | The current Guest theme layer has multiple palettes with limited but inconsistent colour effects. | A Venue Theme Layer may set only accent, accent hover, accent contrast, venue logo and venue hero. Selected surface is derived, not freeform. | Venues can feel recognisable without fragmenting typography, controls, status language, navigation or interaction behaviour. |
| FD-006 | What resolves the muted-text contrast issue? | The audit found muted text can fail contrast in amber, ivory and porcelain Guest palettes. | Normal-size primary, secondary and muted text must meet WCAG AA (4.5:1) on their mapped backgrounds. Invalid venue colour values fall back to MIRA defaults. | Readability is a system rule; it cannot depend on a palette variant or a venue’s input. |
| FD-007 | What spacing and shape grammar should future work use? | Existing CSS contains many close literal spacing and radius values. | Use a 4px micro-step, an 8px primary rhythm, 14 official spacing levels and six radius levels. | It preserves comfortable hospitality surfaces and supports compact Waiter/Admin operations without arbitrary near-duplicates. |
| FD-008 | Which responsive thresholds are authoritative? | Current styles use a broad, inconsistent set of breakpoint values. | Use six canonical breakpoints: 360, 480, 768, 1024, 1280 and 1440px. | The scale covers supported mobile, app caps, tablet transitions and Website containers with a comprehensible future contract. |
| FD-009 | How does shared foundation handle different operational density? | Guest, Waiter and Admin need distinct information density but share a product identity. | Guest is comfortable, Waiter is compact operational, and Admin is efficient data-dense. Shared tokens remain constant; composition rules vary by surface. | This prevents a single generic density model from making dining discovery cramped or operations slow. |
| FD-010 | What is the approved logo source? | The repository contains only a raster welcome-reference image; no original vector logo is available. | Preserve the current raster source without reconstruction. Mark original SVG or transparent high-resolution artwork as **ASSET REQUIRED** before production-grade scaling. | Recreating a brand asset from a cropped raster reference would invent an unapproved logo. |
| FD-011 | How do dark and light contexts share semantic roles? | Dark brand/restaurant and light operational contexts were described, but only dark semantic values were catalogued. | One Design System has two Figma/token modes: `MIRA / Brand Dark` and `MIRA / Operational Light`. The same semantic names resolve to mode values; status semantics remain global. | This supports Guest, Website, Waiter and Admin contexts without creating role-specific design systems or names such as `admin.text.primary`. |
| FD-012 | Which easing values are canonical? | Foundations and Tokens specified different easing values for the same names. | `easing.standard` is `cubic-bezier(.2,0,0,1)`; `easing.enter` is `cubic-bezier(0,0,.2,1)`; `easing.exit` is `cubic-bezier(.4,0,1,1)`. | One named token must always resolve to one value across the foundation contract. |
| FD-013 | What is the canonical elevation category? | Documentation mixed `shadow.*` and `elevation.*` names. | The token category is `elevation.none`, `elevation.subtle`, `elevation.card`, `elevation.overlay` and `elevation.modal`. | CSS implementation may use `box-shadow`, but the design-system token name remains consistent. |
| FD-014 | What is the typography minimum for controls? | A 12px `type.label.s` could have been interpreted as an interactive control label despite the 14px UI minimum. | Essential UI text and interactive labels are at least 14px. The former `type.label.s` is renamed `type.metadata.s`; caption and overline are non-critical metadata or decorative/category text only. | Small supporting text remains available without weakening accessibility and control readability. |
| FD-015 | How are statuses presented across modes? | Global status values alone cannot guarantee legible foreground-on-surface pairs in both modes. | Keep global status base identity values; add mode-aware `foreground`, `surface` and `border` presentation aliases for each status. | StatusBadge, Alert, Toast and InlineValidation need one tested architecture without Guest/Admin-specific names. |
| FD-016 | How is overlay separation tokenized? | Dialog and BottomSheet otherwise need local backdrop opacity values. | Add one mode-aware `color.overlay.backdrop` semantic token used at `z.overlay`. | It creates consistent focus context without local arbitrary RGBA values. |
| FD-017 | How are control dimensions governed? | Components need consistent S/M/L height and 44px hit-area rules, but Foundations had no dimension contract. | Add `control.height.s/m/l` at 32/40/48px and `control.hit-area.min` at 44px. | The scale supports compact operations and touch accessibility without role-specific dimensions. |

## Implementation boundaries

The decisions in this log are future system contracts. They do not authorize changes to existing CSS, UI, components, routes, payments, POS, sessions, tips, stop-list, calls, orders, split logic, cashback or cross-role state.

The source specifications are [MIRA_LINK_FOUNDATIONS.md](MIRA_LINK_FOUNDATIONS.md) and [MIRA_LINK_TOKENS.md](MIRA_LINK_TOKENS.md).
